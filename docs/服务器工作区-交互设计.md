# 服务器工作区 / 文件夹子工作区 — 交互设计与实现说明

> **一台服务器 = 左侧一个工作区；服务器里的某个文件夹 = 它下面的子工作区。**
> 本文描述**已实现**的交互（P0 + P1 已落地），不再只是设计稿。原型：`docs/prototype-服务器工作区.html`（双击打开，内含"已实现版本与原型差异"横幅）。

| | |
|---|---|
| 目标 | 用户能「选一台服务器当工作区」，也能「选服务器里某个具体文件夹当子工作区」 |
| 入口 | 侧边栏页脚新增 **🖥 服务器工作区**（`sidebar.footer.action`，order 41） |
| 关键约束 | 远端路径**永远不能**直接当 DSH 工作区（工作区 = Host 上的本地绝对目录），所以每台服务器 / 每个远端目录都对应一个**本地占位目录** |
| 嵌套 | DSH 客户端只看工作区 `path` 的最长前缀，占位目录嵌套 → 左侧自动呈现父子缩进（需 `分组方式 = 工作区树`） |

---

## 1. 一句话方案

每个工作区在 DSH 里就是一条 `{path, title}` 记录，`path` 是**本地绝对目录**。

- **服务器工作区（父）**：为每台服务器建一个本地占位目录
  `<profile>\remote-ssh-workspaces\<serverId>`，标题 = 服务器名，会话默认 cwd = 该服务器的「默认工作目录」（`remoteRoot`，默认 `~`）。
- **文件夹工作区（子）**：在那个服务器目录**里面**再建一层
  `<…>\<serverId>\<basename>-<hash8(远端绝对路径)>`，标题 = 远端目录名，会话默认 cwd = 该远端绝对路径。

```
srv (ubuntu)                     ← 工作区：…\remote-ssh-workspaces\srv_1a2b3c4d5e6f7a8b
   ├─ app                        ← 工作区：…\srv_1a2b3c4d…\app-1eb37e2b   → 远端 /var/www/app
   └─ deploy                     ← 工作区：…\srv_1a2b3c4d…\deploy-3f9a12cd → 远端 /opt/deploy
srv-root (root)
example-app                        ← 本地文件夹工作区（DSH 原有）
project-a
project-b
```

**为什么这样可行**（`dsh-client-ui-workspace` 的 `owningParentFolder`）：父子关系完全由 `path` 的最长前缀推导，插件不需要自己画树、画缩进、管折叠。代价是它只在 `分组方式 = 工作区树` 下生效；平铺视图下工作区仍然可用，只是并列显示。

## 2. 已实现的交互

### 2.1 入口：侧边栏页脚「服务器工作区」

```
┌ 工作区 ─────────────────── ＋ ┐
│ ▾ srv (ubuntu)               │
│   ├ app                      │
│ ▸ srv-root (root)            │
│ ▾ deepseek                   │
└──────────────────────────────┘
   🖥 服务器工作区 · ⚙ 设置      ← 本插件在页脚只保留这一个入口
```

点它打开一个弹窗（不是菜单），因为流程里有二级界面（远端目录浏览）。页脚不再有第二个入口：

| 控件 | 语义 |
|---|---|
| 页脚 **服务器工作区** | **建**工作区：把整台服务器、或服务器里一个目录，加进左侧工作区列；**添加 / 管理服务器也在这里** |
| 会话行上的 🌐 动作（已连接时还有行首徽标） | **切**这一条会话在哪执行（本地 / 某台服务器），与页脚无关 |

1.0.7 之前的页脚还有一个「执行位置」菜单，里面同样列着服务器、也能添加服务器。两个入口列同一批服务器、且都叫「服务器」，属于同一件事的两个入口，所以删掉了：**加服务器**收进「服务器工作区」面板，「切当前会话」只留在该会话自己那一行（那是唯一能明确“切哪条会话”的地方）。

**取舍（1.0.7 的已知代价）**：DSH 只在**有消息内容**的会话行上留缝 —— `sidebar.session.row.leading` 要求 `!row.archived && !row.blank`，`sidebar.workspaces.session.row.action` 要求 `!row.blank`（`dsh-client-ui-workspace/lib/client.js:1623` / `:1640` / `:1665`）。所以刚建好、还没发过消息的**空对话**那一行上没有 🌐，而页脚那个「执行位置」菜单原本可以指向当前对话（包括空的）。现在要让第一条消息就跑在服务器上，走「服务器工作区」面板：把服务器加为工作区 → 在那个分组里新建对话（它的 cwd 从建出来就在服务器上）。已经发过消息的对话，行上会出现 🌐，随时可以切过去。给空对话补一个专用入口列在 §9。

### 2.2 弹窗第一步：服务器列表

```
┌ 服务器工作区 ─────────────────────────────────────────────┐
│ 把一台服务器、或服务器里的某个目录加为左侧工作区。            │
│ 服务器工作区从服务器的默认目录开始；目录工作区固定在那个远端目录里。│
│                                                           │
│ 服务器                         [管理服务器]※ [＋ 添加服务器]│
│ 「加为工作区」把整台服务器加进左侧；「选择目录…」先浏览…      │
│ ● srv (ubuntu)                       [选择目录…] [加为工作区]│
│   ubuntu@203.0.113.10:22 · 已连接                          │
│   …\profiles\desktop\remote-ssh-workspaces\srv_1a2b3c4d…   │
│ ○ srv-root (root)                    [选择目录…] [加为工作区]│
│   root@203.0.113.10:22 · 按需连接                          │
│                                                           │
│ 已添加的远端目录                                            │
│ app                                                       │
│ srv (ubuntu) · /var/www/app            [打开]    [移除]     │
└───────────────────────────────────────────────────────────┘
```

- 「服务器」与「已添加的远端目录」两块列表数据来自 Host 的 `overview`，弹窗打开时刷新一次，并沿用既有的 5 秒轮询。
- 没有服务器时显示空态：`还没有服务器` + 提示点右上角「添加服务器」，但**「＋ 添加服务器」按钮依然在**（同一块 section 头），不需要先离开面板。
- ※「管理服务器」只在**已有服务器**时出现（`servers.length` 为 0 时不渲染）。零服务器时它那格是空的：管理一台不存在的服务器没有意义，管理视图自身也是同一个空态 + 一个添加按钮，套两层只会让人多点一次。
- 「移除」= 插件不再记住这个远端目录，**并且**删掉它那条工作区注册（左侧那一行跟着消失），和删服务器时对子工作区的级联完全同一条路径。本地占位目录与已有会话都保留，重新选一次同一个目录即可原样加回来（确定性 slug → 同一个本地目录）。有二次确认。

#### 2.2.1 面板内的两个子视图：添加 / 编辑服务器 与 管理服务器

```
┌ 服务器工作区 ─────────────────────────────────────────────┐
│ ‹ 返回   添加服务器工作区                                   │
│ 添加一台 Linux/Unix SSH 服务器。保存后它会成为左侧的一个服务器工作区…│
│ 名称 / 服务器地址 / 用户名 / SSH 端口 / 认证方式 …            │
│                          [取消]      [测试并保存]           │
└───────────────────────────────────────────────────────────┘
```

- **不叠第二个弹窗**，而是把同一个弹窗的正文换成表单或服务器列表（`‹ 返回` 回列表），和远端目录浏览是同一个套路。原因：DSH 的弹窗会把内容 portal 到 `body`，嵌套弹窗的 DOM 在这个弹窗之外，点它内部就可能被外层判定成「点了外面」而把面板一起关掉。
- 面板里的表单用 `sessionId: null` 保存：**只保存服务器，不改任何会话的执行位置**。Host 端 `server.testAndSave` 本来就会为这台服务器建好工作区注册，所以保存完左侧立刻多一行；面板弹出一条提示，用户点那一行的「加为工作区」开始对话。这比自动把当前对话切过去更可预期——一个「管理工作区」的面板不该顺手改动某个对话的执行位置。
- 「管理服务器」在服务器列表里提供 重连 / 编辑 / 删除（1.0.6 已有的 `ServerManager`，原样复用），编辑与「＋ 添加服务器」共用同一张表单。
- 会话行的执行位置菜单里**也**保留这张表单和这个管理视图（`TargetMenu` 底部那两行）。理由：把某条会话指到一台**还不存在**的服务器上时，不该先跑去页脚面板绕一圈；两处渲染同一份实现，没有第二套逻辑。页脚面板是「管理服务器」的主入口，会话行菜单是就地入口，两者不冲突。
- 表单首句会按来源变化：从会话行进来（有 `sessionId`）说「保存只做 SSH 测试并保存连接，当前对话的执行位置不变；要把它切到这台服务器，保存后用这一行的 🌐 菜单选择它」；从面板进来（无 `sessionId`）说「保存后它会成为左侧的一个服务器工作区」。**两条路径都只保存连接、都不动任何会话的执行位置**：1.0.9 之前会话行那条路径在保存成功后补一次 `target.set({ sessionId, target: { type: 'ssh', serverId } })`，于是「编辑 / 重测一台已保存的服务器」变成一次隐式切换，会把用户刚在这条行上选的「本地电脑」再覆盖回去（真实记录里能看到同一条会话 4 次 `local -> ssh`，其中两次间隔 2.6 秒）。切换执行位置只有两个显式入口：这一行的 🌐 菜单里选一台服务器，或在服务器工作区（及其子目录）里新建对话。
- 会话行那个 🌐 菜单是**选择器**，不是说明书（1.0.10）：它原来在「服务器工作区」标题下带一段三行说明（「每台服务器都是左侧工作区里的一个独立分组，组内新建的对话直接在这台服务器上执行」），而且每一行都有第二行副标题（`user@host:22 · 按需连接`），窄栏里第二行会折行——两台服务器的菜单比它挂靠的工作区列表还高。现在：段落删掉；行副标题只写地址（端口不是 22 才出现）；连接状态挪进行 tooltip（行首本来就有状态点）；「本地电脑」和「管理服务器」各占一行；「添加服务器」的副标题缩成「保存后成为左侧工作区」。字号取 DSH 菜单自己的栅格（行 13px / 行高 20px、副标题与章节标签 11px / 15px、卡片内边距 4px、卡片宽 236px），并用双类名选择器（`.dshrs-menu-list .dshrs-menu-sub` 等）压住宿主 portal 卡片里继承下来的正文字号——`Menu` 的 `listClassName` 是挂在宿主卡片上的，宿主的后代选择器优先级高于我们的单个类名。
- 那个菜单**贴着它那行**，并且永远不会跑到窗口顶上（1.0.12，取代 1.0.11 的翻面）。宿主 `Menu` 把 portal 出来的卡片放在 `y = anchor.top`，放不下时**夹取**而不是翻面：`y = min(max(y, 12), 视口高 - 卡片高 - 12)`。卡片高约 250px，于是窗口下三分之一里的任何一行都会把它顶到视口边缘——鼠标往下一动、或者菜单开着时滚动工作区列表，卡片就离开了它那一行。1.0.11 改成「上方空间更大就 `side: "top"`」，结果是把卡片底边贴到行的上沿、顶边顶到窗口顶部（用户 567px 高的列、行在 290px 处时，卡片几乎占满整列），看起来还是「飞到上面去了」。现在横向仍是 `side: "right"` 的右侧飞出（卡片的 `top` 就等于行的 `top`），纵向改为**按行下方的余量给卡片封顶**：`视口高 - 行顶 - 12px 宿主边距 - 12px 卡片自身内边距与描边`，下限 150px。因为宿主对放得下的卡片根本不会夹取，卡片就始终停在行上；靠近窗口底部的行得到的是一个更矮、内部可滚动（`.dshrs-menu-body`）的卡片，而不是一个会跳的卡片。封顶走的是我们自己的 DOM 而不是宿主 prop，所以宿主的第一次量高就已经用上它——没有那一帧的夹取。

### 2.3 弹窗第二步：远端目录浏览器

```
┌ 服务器工作区 ─────────────────────────────────────────────┐
│ ‹ 返回   /var/www/app                                      │  ← 返回按钮 + 当前路径（等宽字体，可选中复制）
│ srv (ubuntu)：点目录进入，选定后把这个目录加为工作区。…      │
│ ┌───────────────────────────────────────────────────────┐ │
│ │ ..                                     上级目录        │ │  ← 有 parent 时才出现
│ │ config/                                               │ │
│ │ storage/                                              │ │
│ │ vendor/                                软链接          │ │  ← 符号链接目录可进，标出来源
│ └───────────────────────────────────────────────────────┘ │
│                    [ 把这个目录加为工作区 ]                 │
└───────────────────────────────────────────────────────────┘
```

- **只列目录**，不列文件；`~`、相对路径、`/` 绝对路径都由 Host 端的 `spellRemotePath` 解析成绝对路径；返回的是 SFTP `realpath`，所以符号链接会显示成它指向的真实路径。
- 主按钮作用于**当前所在目录**（不要求先选中某一行）。
- 读取中 / 空目录 / 无权限 / 目录不存在都在就地显示，不弹新窗口；`‹ 返回` 回到服务器列表。
- **已实现版本的简化**：没有面包屑点击跳转、没有手输路径输入框、没有「显示隐藏目录」开关（原型里有，见 §9）。目录很多时按名字排序并截断到 500 项，超出时提示"仅显示前 N / M 项"。

### 2.4 「加为工作区」之后发生什么

```
点按钮 → RPC workspace.addServer / workspace.addFolder
      → Host：mkdir 占位目录 → workstation registry.create(dir, title)
              → 写 store（folderWorkspaces）→ 返回 {workspaceId, dir, title}
      → Client：等自己的工作区列表 snapshot 追上（最多 12 × 200ms）
              → uiWorkspace.openWorkspace(workspaceId)
              → DSH 原生行为：复用该工作区里的空会话，或新建一条会话并展示
```

- 用的是 **DSH 原生"打开工作区"**（`uiWorkspace.openWorkspace`），不是自己跳转：它会复用已有的空白会话，否则在该工作区新建一条，所以用户点完就落在一条**跑在服务器上**的会话里。
- 两个入口都自动打开（不是"只 toast 不打开"）——因为 `openWorkspace` 就是 DSH 里点一个工作区的既有行为。
- 客户端的工作区列表是 Host 推流（`remote.workspace.follow`）的镜像，刚建完记录时镜像可能还差一帧，`connectWorkspace` 会抛 `unknown workspace <id>`。插件对它**有界重试**（12 × 200ms，期间强制刷新 `overview`），仍不成功才降级提示"已加为工作区，左侧列表还没同步出来，稍后手动打开"，不会假装成功。
- 若当前客户端根本没有工作区导航服务，同样降级提示（工作区记录已经建好了，刷新页面就能在左侧看到）。

## 3. 命名与数据

| 项 | 规则 |
|---|---|
| slug | `<basename>-<hash8(规范化后的远端绝对路径)>`，如 `/var/www/app` → `app-1eb37e2b`；`/home/ubuntu` → `ubuntu-3b2485e5`；`/` → `dir-2a0c975e` |
| 规范化 | 先 `posix.normalize`，再剥掉末尾 `/`（除非是根），然后才哈希 —— `/home/ubuntu` 与 `/home/ubuntu/` 必须映射到同一条 |
| 确定性收益 | 同一远端路径重复选择 → `resolveByPath` 命中已有工作区 → 直接打开，不产生重复行 |
| 标题 | 默认 = 远端目录名（`app`）；重名时依次退化为 `parent/name`、`www/app (2)`；用户已改过的标题在重新同步时**不覆盖** |
| 目录名安全 | 非法字符 `<>:"/\|?*` 与控制字符替换成 `_`，每段截断到 40 字符（Windows 路径长度） |
| 权威映射 | 存在插件自己的 store 里（`state.json` 的 `folderWorkspaces`），不靠目录名反推 |
| schema | `SCHEMA_VERSION = 9`；v8→v9 迁移会补 `folderWorkspaces: []`，丢弃未知服务器 / 重复的记录 |

```jsonc
// <profile>/.dsh-remote-ssh/state.json
"folderWorkspaces": [
  { "serverId": "srv_1a2b3c4d5e6f7a8b",
    "remotePath": "/var/www/app",
    "title": "app",
    "workspaceId": "…" }
]
```

占位目录是**空的**：它只是让 DSH 记住归属并推导嵌套；文件、命令、终端全在服务器上（沿用 README 的既有约定）。

## 4. 为什么这么设计（三个被否掉的方案）

### 4.1 入口为什么不是「＋ 添加工作区」

`sidebar.workspaces.directoryFlow` / `conversation.hero.workspace.directoryFlow` 是**多占用**插槽，理论上可以再加一项，但实际上：

- DSH 自带的 `dsh-client-ui-directory-picker-native` 就注册在这里，且是**无渲染**的 —— 它在 `open` 边沿自动弹出系统对话框；
- `dsh-client-ui-directory-picker-browse` 也占同一个洞，弹出应用内选择器。

也就是说这个洞的语义是"**点击即弹选择器**"，而不是"列一个菜单让用户选去哪"。第三方再插一脚，用户点一次 `＋` 会同时触发多个选择器/流程。因此本插件**不占**这些洞，改为在页脚新增一个独立入口「服务器工作区」，互不干扰。

### 4.2 为什么不是 `inject: { required, optional }`

初版诊断曾经以为"加一行 `optional: ['workspaceRegistry']` 就能修好"。**cordis 4.0.4 没有这个对象形式**。真正生效的写法是：

```js
// src/index.js:118-130
const registryReady = (() => {
  let settle
  const promise = new Promise(resolve => { settle = resolve })
  if (typeof ctx.inject === 'function') ctx.inject(['workspaceRegistry'], inner => settle(inner))
  else settle(undefined)
  return promise
})()
```

`ctx.inject(deps, cb)` 会开一个子 fiber：**能看到兄弟 fiber 提供的服务**，而且无论服务早挂还是晚挂都会在挂载时触发 —— 同时解决了"看不见"和"挂载时机"两个问题。`workspaceContext()` / `requireWorkspaceContext()` 就基于它（`src/index.js:132`、`143`）。

### 4.3 客户端为什么用 `ctx.get('uiWorkspace')`

客户端动态包拿到的 `ctx` 不是原始 cordis Context，而是一个白名单 Proxy：

- 允许的动词只有 `effect / on / once / provide / timeout / interval / setTimeout / setInterval / throttle / debounce`；
- `ctx.get(name)` 是**可选查找**，无需声明；
- 直接读未在 `inject` 数组里声明的服务会抛 guard 错误并上报包失败；
- **`ctx.inject` 在客户端不可用**（读它就等于读一个未声明的服务）。

所以客户端只能 `ctx.get('uiWorkspace')`（以及 `ctx.get('workspaces')` 读客户端自己的镜像）。另外渲染器的 `inject` 结果按条目 **memoize**（只求值一次），若在注入时取服务，服务晚挂载就会永远拿不到 —— 因此入口注入的是**函数**（`resolveUiWorkspace` / `resolveWorkspaces`），在用户点击时才求值（`client.js:1541–1549` 定义，`:1555` 注入）。

`@deepseek-ai/dsh-client-ui-workspace` 也**没有**被加进 `package.json` 的 `dsh.client.inject`：那是 loader 元数据，缺了会把整个包 park 掉，而不是只少一个入口。

1. **重启 DSH** 后：左侧工作区列出现 `srv (ubuntu)`、`srv-root (root)`（每个已保存的服务器一条）。

## 8. 部署

插件在 profile 里是**打包安装**的（`%USERPROFILE%\.dsh\profiles\desktop\package.json`）：

```json
"dsh-remote-ssh": "file:<tgz 目录>/dsh-remote-ssh-1.0.7.tgz"
```

`pnpm-workspace.yaml` 里 `nodeLinker: hoisted`，所以实际运行的是
`…\profiles\desktop\node_modules\dsh-remote-ssh\` 这个解包目录。**改仓库源码不会立刻生效**，要让 GUI 看到新版本：

```powershell
cd <本仓库目录>
node ./scripts/build-host.mjs                 # src → dist/index.js
npm pack                                      # 产出 dsh-remote-ssh-<version>.tgz
node <部署脚本>.mjs 1.0.7
# 上面这步会：把 tgz 放到该目录、算出 sha512 写回 profile 的
# package.json 与 pnpm-lock.yaml、解包到 node_modules\dsh-remote-ssh（先暂存再换目录，被占用时报错而不留半个安装）
# 脚本从 profile 自己的 package.json 读出「当前版本」来替换，所以升版本不需要改脚本
```

最后**重启 DSH**（Host 侧代码只在启动时加载一次；`client.js` 也要靠重启后的页面加载）。`client.js` 本身不需要构建，Host 直接从包目录读它。检查是否生效：安装目录里的 `client.js` 与仓库里的必须同哈希（脚本会打印两边 sha256 前 16 位）。

### 第三轮（1.0.7 交互收缩，2 条设计缺陷 + 1 条测试能力缺口）

用户看完实机截图后判定：页脚同时出现「服务器工作区」和「执行位置」，两个入口都列同一批服务器、都能加服务器，属于同一件事的两个入口。收缩时发现：

|---|---|---|
| S1 | 页脚「执行位置」菜单的 `sessionId` 只能靠插槽额外注入的 `useSessions` 取到；一旦那个注入缺席（旧 Host、或槽位契约变动），`canSwitch` 恒为 false，整段列表点不动且只给一句"请先打开一个对话"——**一个看起来能切、实际切不动的入口** | 直接删掉这个入口：能明确"切哪条会话"的只有会话行上的动作，它拿到的 `sessionId` 来自行本身 |
| S2 | 面板里的「添加服务器」原来挂在页脚另一个菜单里，用户要先开一个菜单加服务器、再开另一个菜单管服务器 | 面板 section 头加 `[管理服务器] [＋ 添加服务器]`，两者都作为**同一个弹窗**的子视图（不用第二个 Modal：DSH 的弹窗 portal 到 `body`，嵌套弹窗的 DOM 在外层之外，点它内部可能被判定为"点了外面"而把面板关掉） |
